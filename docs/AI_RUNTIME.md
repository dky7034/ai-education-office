# 계정 제한 AI 서버 실행 설정

운영자가 비공개 설정을 명시한 경우에만 영구 AI 큐와 기존 접수 화면을 Codex 실행 어댑터에 연결합니다. 기본값은 비활성입니다. 현재 클라우드 환경에는 제품 설정을 등록하지 않았으며 실제 모델 호출은 미검증입니다. 구현 검사는 별도 DB와 가짜 stdio 실행기만 사용했습니다.

## 활성화 전 준비

1. [제품용 AI 연결 점검](AI_SERVICE_CHECK.md)의 제품 키·비용/사용량 제한·데이터 전송/보존 정책·실행 호스트 격리 검토를 완료합니다. 개발 세션 인증을 서비스 인증으로 사용하지 않습니다.
2. 별도의 가상 데이터 단일 실제 호출을 수행하고 정상 종료·사용량·호환성을 확인합니다. `serviceCallVerified`는 이 검증을 마쳤다는 운영자의 확인이며 프로그램이 제공자 기록을 증명하는 값은 아닙니다.
3. DB·원본·출력의 비공개 백업과 복구 절차를 준비합니다. 처음에는 별도 시험 DB와 가상 업무만으로 서버 접수→실행→결과 검토→중단→재시작 흐름을 확인합니다.
4. [운영 설정 예시](../config/ai-runtime.example.json)를 저장소 밖 비공개 디렉터리에 복사하고 권한을 0600으로 지정합니다. false 확인 항목을 검토 없이 true로 바꾸지 않습니다.

| 필드 | 기준 |
| --- | --- |
| version | 정수 1 |
| enableDispatch | 명시적으로 서버 접수/큐 실행을 허용할 때 true |
| serviceCallVerified | 해당 모델·정책·호스트로 실제 가상 데이터 호출을 확인한 뒤 true |
| serviceConfigFile | 기존 제품 설정 JSON의 절대 경로, 제품 키는 별도 파일 |
| policyId | 비밀이 아닌 정책 식별자, 영숫자/밑줄/하이픈 1~128자 |
| allowedAccountIds | 허용할 기존 계정의 소문자 UUID 1~20개, 중복·와일드카드 불가 |

허용 계정 ID는 권한 있는 운영자가 해당 사용자의 로그인 세션 응답 `GET /api/auth/session`의 `user.id`로 확인합니다. 사용자명이나 세션 쿠키를 허용 목록에 넣지 않습니다. 계정 목록을 HTTP에 공개하거나 관리하는 API는 추가하지 않았습니다. 운영 파일과 제품/키 파일은 현재 유효 사용자 소유의 정확히 0600 일반 파일이어야 합니다. 링크/크기/UTF-8 검사는 기존 비공개 파일 판독기를 공유하며 운영 파일은 최대 8KiB입니다. 부모 디렉터리·바이너리 신뢰성과 실제 격리 실효성은 운영자 책임입니다.

## 서버 시작

제품/운영 설정을 모두 완성한 별도 검증 호스트에서 다음처럼 시작합니다.

```sh
npm run build
OFFICE_AI_RUNTIME_CONFIG=/secure/office/runtime.json npm run preview
```

설정 파일을 생략하면 키 파일을 읽거나 실행기를 만들지 않고 기존처럼 신규 AI 접수·디스패치를 비활성으로 유지합니다. `OFFICE_AI_CONFIG`는 점검 명령 전용이며 서버 활성화로 이어지지 않습니다. 빈 문자열·잘못된 파일·검토 미완료·잘못된 계정/정책·제품 설정 실패는 **DB를 열거나 수신 포트를 열기 전에 종료 코드 1**로 끝냅니다. 실패 시 무설정 모드로 조용히 대체하지 않으며 파일 경로·키·원격 오류를 출력하지 않습니다.

설정 로드는 프로세스/모델 호출을 하지 않습니다. 다만 서버가 시작되면 현재 정책·모델과 일치하고 허용된 계정의 **기존 queued 기록도 실행 대상**입니다. 대기 중인 업무를 먼저 확인하고 필요하면 취소한 뒤 활성화합니다. 서버 시작 때 실제 인증을 시험하는 자동 호출은 없습니다. 시작 로그의 접수 설정은 실제 연결 성공을 뜻하지 않습니다. 기존 health는 서버 생존 여부이며 실제 모델 연결 검증용이 아닙니다.

## 접수와 실행 제한

- 허용 계정의 자기 업무에서만 capability가 configured/codex로 표시됩니다. 다른 계정은 disabled이며 신규 접수는 503입니다. 읽기·완료 초안·검토·취소는 기존 소유권 범위에서 계속 가능합니다. 허용 목록에서 빠져도 같은 요청 키의 과거 응답 재확인은 새 실행 없이 가능합니다.
- 브라우저는 기존의 명시적 AI 초안 접수 동작만 사용합니다. 요청 본문은 빈 객체이며 모델·키·정책·허용 계정·임의 프롬프트를 받지 않습니다. 제공자에게 전송하는 입력은 접수 시 저장된 제목·업무 종류·요청 내용이며 첨부는 보내지 않습니다. 시각화·새로고침·조회가 새 AI 실행을 만들지 않습니다.
- 큐가 실행을 확정하기 전 같은 트랜잭션에서 계정 허용 여부와 업무 소유권·접수 당시 모델/정책을 다시 확인합니다. 허용이 제거된 대기는 failed/account_not_enabled로 종료하고 running 전환이나 실행기 생성/호출을 하지 않습니다. 정책·모델 변경은 기존 configuration_changed 계약을 따릅니다. 종료된 기록은 재접수하지 않습니다.
- 기존 전역 동시 실행 1개·전체 활성 20개·계정당 활성 5개·lease·시간 제한·요청 중복 방지를 유지합니다. 이 제한은 누적 금액 상한이 아니며 제공자 측 제한이 별도로 필요합니다. 실행기는 명시적인 제품 키만 사용하고 부모 환경의 인증을 상속하지 않습니다.
- 결과/상태는 기존 AI 실행·초안 검토·계정별 이벤트로 보관합니다. 결과는 검수 필요이며 승인으로 재실행·외부 전송·파일 반영을 하지 않습니다. 기존 정량 집계·업무 접수의 executionMode는 AI 신규 접수 가능 여부를 대신하지 않으며 AI 패널 capability/개별 실행 상태를 확인합니다.

## 중단·변경·비활성화

운영 설정은 시작 때만 읽고 HTTP·큐에는 복사본을 전달합니다. 변경은 정상 종료 후 재시작해야 하며 hot reload는 없습니다. 키·모델·비용/전송/격리 정책 변경 시 정책 식별자를 새로 정하고 실제 호출 검증을 다시 수행합니다.

SIGINT/SIGTERM은 HTTP 수신 중단→큐 정리→DB 닫기 순서로 처리합니다. 진행 중 실행은 interrupted/server_stopped, 원격 상태 unknown으로 남기며 재시작해 자동 재전송하지 않습니다. 사용자 취소는 cancelling과 원격 interrupted 확인을 구분합니다. 프로세스 종료는 원격 과금 중단 증명이 아닙니다. 포트 열기 실패도 큐를 정리하고 종료합니다.

비활성화하려면 서버를 정상 종료하고 `OFFICE_AI_RUNTIME_CONFIG` 없이 다시 시작합니다. 대기 기록은 보존되며 조회·취소와 미확정 복구만 제공합니다. 허용 계정 제거 후 활성 모드로 재시작하면 해당 대기는 실행 전 실패로 종료합니다. DB 초기화나 기존 결과/검토 삭제는 필요하지 않습니다.

실제 제공자 인증·모델 호환·비용·개인정보 처리·공개 배포·실제 원격 실패 복구는 여전히 미검증입니다. 설정과 합성 검사의 성공을 운영 준비 완료로 표시하지 않습니다.

브라우저 회귀 검사는 Playwright 기본 설정에서 OFFICE_AI_RUNTIME_CONFIG를 제거해 운영 설정을 상속하지 않습니다. 운영 연결 프로세스 검사는 별도 임시 DB·가짜 키·합성 실행기를 명시적으로 지정합니다.
