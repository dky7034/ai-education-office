### 실제 브라우저 시나리오

1. 한국어 문서·화면, 직원 버튼 6개, Phaser 캔버스 표시 → 캔버스의 직원 클릭 → 직무 정보 확인 → 공지·메일 업무 배정 → 이동 상태 → **이동한 위치에서 캐릭터 클릭** → 완료·시연 이력·로그 확인. 페이지 자바스크립트 오류 없음 확인.
2. 6가지 업무 버튼을 각각 눌러 올바른 담당자와 업무명 확인 → 초기화 → 오류 상황 시연 → 오류 상태·재시작 가능 확인 → 초기화 후 이전 타이머가 로그를 복원하지 않는지 확인 → 새로고침 후 이력 초기화·수평 넘침 없음 확인.
3. ‘동작 줄이기’ 미디어 설정에서 안내 대화상자 열기·Esc 닫기, 키보드 Enter로 직원 선택, 일정 업무 시연 시작 확인.

테스트 설정은 데스크톱 1536×1100과 Pixel 7 장치 프리셋을 사용합니다. 이는 실제 스마트폰·Windows·Safari 테스트를 대신하지 않습니다. reduced motion 검사에서는 시연 시작과 키보드 조작까지 확인하고 전체 종료 흐름은 기본 모드에서 확인했습니다.

## 문제 발견 및 수정

- 최초 빌드 시 Vite 8의 `manualChunks` 타입이 기존 객체 형식을 받지 않았습니다. 함수 형식으로 수정하고 재빌드했습니다.
- 최초 브라우저 검사에서 중앙 복도에 겹쳐 있던 직원 클릭이 다른 직원으로 연결됐습니다. 대기 위치를 각 사무실 안으로 분리하고 캔버스 입력 검사를 재실행했습니다.
- 이동 경로가 문과 복도를 통과하도록 보완했고, 오류 시에는 이동을 멈추도록 했습니다.
- Playwright 전용 브라우저 다운로드는 네트워크 정책상 HTTP 403으로 차단됐습니다. 검증을 끄지 않고 이미 설치된 시스템 Chromium을 사용해 테스트를 완료했습니다. 현재 개발 흐름에 추가 네트워크 허용·키가 필요하지 않습니다.

## 직접 확인하는 순서

1. 저장소 루트에서 `npm ci`, `npm run dev`를 실행하고 Vite가 출력하는 개발 서버 주소를 엽니다.
2. 상단의 ‘시뮬레이션 모드’와 실제 AI·파일·발송 미실행 안내를 확인합니다.
3. 6가지 업무를 하나씩 선택하고 담당 직원이 작업 구역과 공용 검수 공간으로 이동하는지 확인합니다. 약 15초 후 다음 업무를 선택할 수 있습니다.
4. 캔버스 직원과 지도 아래 직원 버튼을 눌러 이름·담당 업무·현재 상태·최근 시연 이력을 확인합니다.
5. 오른쪽 단계 표시와 하단 로그를 확인합니다. 퍼센트 진행률·실제 결과물·자동 발송은 없습니다.
6. 시연 중 상단 설정 아이콘 → ‘오류 시연’을 누르고 오류 안내를 확인합니다. 다른 업무를 선택해 새로 시작할 수 있습니다.
7. ‘시연 초기화’, 사용 안내 대화상자의 Esc 닫기, Tab·Enter 조작, 좁은 화면과 동작 줄이기 설정을 확인합니다.

## Phase 3 첫 단계 검증

- 임시 SQLite DB에 업무와 이벤트를 저장하고 서버를 완전히 종료·재시작한 뒤 같은 세션으로 ID·요청 내용·이벤트를 복원했습니다.
- 같은 요청 키의 동시 POST는 업무·이벤트를 한 건만 만들고, 같은 키·다른 내용은 409로 거부했습니다.
- 다른 계정은 업무의 목록·상세·이벤트를 조회할 수 없었습니다. 같은 계정은 다른 브라우저에서 이력을 복원합니다. 세션 없는 쓰기, 외부 Origin, 잘못된 본문·헤더, 크기 초과 요청을 거부했습니다.
- 실제 브라우저에서 폼 저장 → 담당 역할·접수 이벤트 표시 → 새로고침 후 선택 업무 복원을 확인했습니다.
- 서버 연결 실패 시 오류와 비활성 폼을 확인하고, 연결 복구 후 재시도했습니다. POST를 서버까지 보낸 뒤 응답만 유실시키고 같은 폼으로 다시 제출해 업무·이벤트가 한 건인 것을 확인했습니다.
- API/UI 테스트는 임시 DB 또는 `database/e2e.sqlite`를 사용합니다. 기본 DB의 사용자 업무를 테스트 중 초기화하지 않습니다.
- 단일 HTML은 저장 API를 호출하지 않고 시연 전용 안내를 표시합니다. 서버 연동 앱에서만 업무 요청·영구 저장을 제공합니다.
- 개발 프록시의 Host 변경으로 정상 요청도 Origin 검사에서 403으로 거부됨을 발견했습니다. `changeOrigin: false`를 명시하고 실제 개발 서버 회귀 검사 4개를 통과했습니다. Origin 검사를 완화하지 않았습니다.

## 클라우드 환경 재사용

환경 설정 초안에 `install_script`와 `start_skill`을 저장했습니다. 현재 스크립트로 `npm ci`·프론트엔드/백엔드 타입 검사·당시 24개 테스트·두 앱 빌드·단일 HTML 생성을 통과했습니다. `npm run dev`로 API와 Vite를 함께 시작하고 `/api/health` 프록시 응답과 브라우저 내 Origin·입력 검증을 확인했습니다. 기본 DB에 테스트 업무를 넣지 않고 별도 DB로 업무 화면을 촬영했습니다.

의존성과 빌드 산출물은 준비했지만 실행 중인 서버 프로세스는 다음 세션에 유지된다고 가정하지 않습니다. 환경 설정에서 변경 내용을 검토·저장하고 환경을 게시해야 재사용 구성과 스냅샷을 활성화할 수 있습니다. 초안 저장은 런타임 적용·환경 게시·웹앱 공개 배포를 실행하지 않으며 새 작업에서의 복원은 아직 검증하지 않았습니다.

## HTML 미리보기 오류 후속 수정

채팅 HTML 미리보기의 ‘시각화 내부에서 오류가 발생했습니다’ 제보에 따라 서버 검증 외에 격리 iframe 검사를 추가했습니다. 개발용 `frontend/index.html`은 Vite의 TSX 변환·패키지 해석을 전제로 하므로 직접 공유하는 파일로 적합하지 않습니다. `npm run build:preview`로 자바스크립트·스타일을 모두 인라인한 `preview/index.html`을 생성하도록 구성했습니다.

격리 iframe에서 업무 버튼 클릭 시 `crypto.randomUUID is not a function` 예외와 시연 미시작을 실제 재현했습니다. 시뮬레이션 ID를 시간·세션 카운터로 생성하도록 수정했습니다. 이 ID는 인증이나 실제 영구 업무 식별에 사용하지 않습니다.

`npm run test:preview`는 일반 문서·격리 iframe × 데스크톱·모바일의 **4개 테스트**로 사무실·직원 6명 표시, 업무 시연 시작·완료, 자바스크립트 오류 없음, 외부 HTTP 요청 없음을 확인합니다. 이 검사는 채팅 제품 자체의 렌더러를 직접 실행한 것은 아닙니다.

최초 `file://` 검사는 관리형 Chromium 정책의 `ERR_BLOCKED_BY_ADMINISTRATOR`로 실행할 수 없었습니다. 정책을 우회하지 않고 HTML 내용을 문서 및 iframe에 로드해 앱 실행을 검사했습니다. 따라서 이 머신에서 실제 파일 URL 열기가 통과했다고 주장하지 않습니다.

## 계정 인증·복구 검증

- 회원가입·로그인·로그아웃과 실패 메시지, 7일 세션·로그인 시 교체·서버 측 회수·만료를 검사했습니다. 같은 계정으로 다른 브라우저에서 같은 업무를 조회하고, 다른 계정의 상세·이벤트·저장 범위를 차단했습니다.
- 비밀번호를 무작위 salt의 scrypt 해시로만 저장하고, 계정별 salt 차이와 비밀 필드 미노출을 확인했습니다. 운영 쿠키의 Secure·HttpOnly·SameSite·Path·만료 속성을 확인했습니다. 실제 HTTPS 배포를 검증한 것은 아닙니다.
- 복구 코드 재발급에는 현재 비밀번호를 요구합니다. 비밀번호 복구 후 과거 비밀번호·복구 코드·모든 기존 세션이 무효화되고 새 코드로 교체되는 것을 확인했습니다. 같은 코드의 동시 사용은 한 건만 성공했습니다.
- v1 형식의 합성 DB를 만들어 v2 마이그레이션 후 원래 ID·내용·이벤트를 확인했습니다. 원래 쿠키 없는 가져오기·다른 계정의 재가져오기를 차단했고, 같은 중복 방지 키가 있는 계정으로도 기록을 보존해 가져왔습니다.
- 브라우저에서 회원가입·현재 비밀번호 확인 후 코드 재발급·로그아웃·잘못된 로그인·코드 복구·재로그인·새로고침과 명시적인 기존 이력 가져오기를 검사했습니다.
- 로그인 폼이 펼쳐져 캔버스가 이동하면 Phaser의 캐시 좌표가 맞지 않던 문제를 재현했습니다. 레이아웃·스크롤·마우스/터치 입력 전에 좌표를 갱신하도록 고쳐 직원 클릭 회귀 검사를 통과했습니다.
- 비밀번호·복구 코드·세션 값은 검증 보고나 화면 기록에 넣지 않습니다. 계정·업무 테스트는 합성 입력과 전용 DB만 사용합니다.
- 실제 개발 DB도 보호된 별도 경로에 백업하고 무결성을 확인한 뒤 v2로 갱신했습니다. 백업의 기존 업무·이벤트 ID와 내용을 비교해 보존을 확인했고, SQLite quick_check·외래 키 검사와 개발 프록시의 비로그인 401 응답을 확인했습니다. 테스트 계정을 기본 DB에 만들지 않았습니다.

## XLSX/CSV 원본 첨부 검증

- UTF-8 BOM·한글 파일명·원본 바이트·SHA-256·목록 및 서버 재시작 후 다운로드를 별도 임시 DB·폴더에서 확인했습니다.
- 합성 ZIP fixture 외에도 openpyxl로 생성한 정상 XLSX의 형식 검증을 확인했습니다.
- 빈 파일, 잘못된 확장자·경로 파일명·UTF-8·인용 CSV, 일반 ZIP·손상 XML·CRC·매크로·압축 해제 용량 초과를 거부했습니다. 5MiB 경계는 허용하고 초과 전송은 413으로 차단했습니다.
