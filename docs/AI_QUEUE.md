# AI 텍스트 초안 실행 기록·큐

2026-10-22 기준, 스키마 v10에 AI 전용 큐·실행 이력·결과 보관과 계정별 API를 추가했습니다. 기존 정량 집계 큐·파일·검토 기록은 그대로 사용합니다. **기본 서버는 AI 신규 접수와 디스패치가 비활성**입니다. 실제 모델 호출·운영 인증은 아직 검증하지 않았습니다. 업무별 [실행 이력·초안 화면](AI_UI.md)은 합성 기록으로 검증했습니다. 합성 실행은 mode=synthetic, 실제 Codex 등록은 mode=codex로 기록하며 서로 바꾸지 않습니다.

## API

모든 경로는 로그인·현재 업무 소유권을 검사합니다. 읽기는 no-store이며 쓰기는 JSON, X-Office-Request: 1, 같은 Origin 정책을 사용합니다.

| 요청 | 동작 |
| --- | --- |
| GET /api/jobs/:id/ai-runs | 계정/업무의 실행 목록·페이지와 서버 설정 유무 |
| POST /api/jobs/:id/ai-runs | 저장된 업무로 텍스트 초안을 접수, 본문 `{}`와 Idempotency-Key 필수 |
| GET /api/jobs/:id/ai-runs/:runId | 실행 메타데이터·영구 상태 이력 |
| GET /api/jobs/:id/ai-runs/:runId/result | 완료된 텍스트·SHA-256·needsReview=true·mode |
| POST /api/jobs/:id/ai-runs/:runId/cancel | 본문 `{}`로 대기 취소 또는 실행 중단 요청 |

목록은 limit=1~20, offset=0 이상이며 다른 쿼리·중복/배열 쿼리는 400입니다. 상세/결과/쓰기에는 쿼리를 받지 않습니다. 소유하지 않은 업무/실행은 404, 미로그인은 401입니다. 새 접수 202, 같은 요청 재생 200, 키 충돌/활성 업무 중복 409, 전체 20개·계정당 5개 초과 429, 실행 미설정 503입니다. 비활성 상태에서도 기존 실행의 조회·같은 요청 재생·취소는 가능합니다.

클라이언트는 모델·인증 키·프롬프트·실행 모드를 전달할 수 없습니다. 입력은 접수 시점의 업무 종류·제목·요청 내용과 고정 안내문을 합쳐 UTF-8 16KiB 이내로 저장합니다. 원본 첨부는 읽거나 AI에 보내지 않습니다. 현재는 파일 처리나 설문 전체 보고서가 아닌 **업무 요청의 텍스트 초안**만 지원합니다.

## 실행 기록과 중복 방지

- ai_runs는 소유 계정/업무·요청 키·입력 snapshot·실행 모드·모델·policyId·상태·원격 상태·thread/turn ID·시간·결과를 저장합니다. 인증·쿠키·세션·프록시 정보는 저장하지 않습니다. 입력과 생성 본문은 개인정보를 포함할 수 있으므로 DB·백업을 비공개로 관리해야 합니다. DB는 암호화되지 않습니다.
- `(account_id,request_key)`가 유일합니다. 같은 키와 업무는 서버 재시작·설정 비활성 후에도 같은 실행을 반환하고, 다른 업무에 재사용하면 충돌합니다. 계정/업무별 대기·실행·중단 중 기록도 한 개만 허용합니다.
- 큐는 실행 전에 running 전환을 트랜잭션으로 커밋하고 그 실행 ID를 어댑터 상관관계 키로 **한 번만** 전달합니다. claim 이후 프로세스가 죽어 실제로 호출했는지 모호해도 재전송하지 않습니다. 사용자가 종료된 업무를 새 요청 키로 명시적으로 다시 접수하는 것은 별도 새 실행입니다.
- 입력·실행 모드·설정 식별자는 변경할 수 없습니다. 완료/실패/취소/중단/시간 초과 상태는 확정 후 수정하지 않으며 상태 이력은 append-only입니다. 완료 텍스트와 해시를 상태 전환과 함께 저장합니다. 결과 조회는 길이·해시를 다시 확인합니다. 해시는 승인·진위 보증이나 서명이 아닙니다.
- 상세/목록에는 입력 snapshot·계정 ID·요청 키·policyId를 노출하지 않습니다. 소유권은 접수·조회·claim·최종 확정 때 확인합니다. 결과 본문을 API로 반환하는 것은 사람이 검수했다는 뜻이 아닙니다. 아직 기존 정량 집계의 승인/반려 API와 연결하지 않았습니다.

## 상태와 복구

queued → running → completed/failed/timed_out이 기본 흐름입니다. 대기 취소는 cancelled, 실행 중 취소 요청은 cancelling입니다. 중단 요청 접수와 실제 원격 종료를 구분합니다. 원격 interrupted가 확인되지 않으면 unknown 또는 실제 completed 상태와 interrupt_unconfirmed를 보관하고 결과 본문을 버립니다. 이미 확정된 결과에 대한 취소는 상태를 바꾸지 않습니다.

ai_queue_lease는 10초 lease와 소유자 fencing을 사용합니다. 기본 250ms마다 갱신하며 한 큐만 claim/확정할 수 있습니다. 새 소유자가 lease를 인수하면 running/cancelling은 interrupted·restart_interrupted·remoteStatus=unknown으로 확정합니다. **대기였던 작업만** 같은 mode/model/policyId일 때 이어 실행합니다. 설정이나 소유권이 바뀌면 실행하지 않고 실패로 기록합니다. 비활성 서버는 복구와 조회/취소만 수행하며 대기는 유지합니다.

lease를 잃은 큐는 로컬 실행기를 닫고 늦게 도착한 결과를 확정하지 않습니다. 정상 서버 종료도 실행기를 닫고 interrupted/server_stopped로 기록하며 재시작 때 재실행하지 않습니다. 큐의 기본 전체 시간 제한은 130초이고 로컬 정리를 기다린 뒤 확정합니다. 정리 실패는 cleanup_failed이며 같은 프로세스에서는 다음 작업을 디스패치하지 않습니다.

lease와 로컬 종료는 제공자 측 처리/과금 중단을 증명하지 않습니다. 이벤트 루프 중단·네트워크 단절·강제 종료 동안 원격 실행이 계속될 수 있습니다. 따라서 interrupted/취소 미확정 기록은 확인 후 재접수해야 하며 외부 시스템 전체에 걸친 exactly-once 보장은 없습니다. 자동 재시도·산출물 외부 반영은 구현하지 않았습니다.

## 영구 알림과 정량 집계 구분

AI 상태 이력은 같은 DB 트랜잭션에서 기존 계정 이벤트에 기록합니다. type=run.changed, fileId=null, runId=AI 실행 ID, state=ai.queued/ai.running 등이며 입력·결과·원격 오류를 포함하지 않습니다. 기존 WebSocket의 커서 재생을 그대로 사용합니다. 재생은 HTTP 쓰기나 AI 호출을 재전송하지 않습니다.

기존 오피스·목록의 집계/검토 건수는 정량 집계 전용입니다. AI 알림이 와도 AI 완료를 정량 집계 완료로 표시하지 않습니다. 업무 상세의 AI 패널에서 실행 이력·초안을 표시합니다. 생성 텍스트를 HTML로 실행하지 않고 검수 필요 표시와 원격 취소 미확정을 안내합니다. AI 상태의 오피스 캐릭터 연결은 후속 작업입니다.

## 서버 구성과 운영 제한

createAiQueue(store)는 디스패치 비활성입니다. 운영 코드에서만 검증된 AiRegistration을 전달하고 같은 queue.config를 createApp의 aiConfig로 전달해야 접수/실행이 연결됩니다. configured는 서버 등록 여부이며 인증 유효성·모델 성공이나 현재 lease 소유권을 뜻하지 않습니다.

codexAiRegistration은 [Codex 어댑터 설정](CODEX_ADAPTER.md)의 명시적인 서비스 키·모델·비용/전송/호스트 격리 검토 설정과 비밀이 아닌 policyId를 요구합니다. 현재 server.ts는 이를 만들지 않으며 환경의 개발 인증을 가져오지 않습니다. 정책·모델·데이터 전송 조건이 바뀌면 policyId를 새로 정해야 합니다. 실행기 factory는 프로세스를 시작하지 말고 run 호출 뒤 실행해야 합니다. 컨테이너·네트워크·비용 한도·개인정보 정책과 실제 합성 호출 검증 전에는 활성화하지 않습니다.

기본 서버/테스트 큐·DB·입력·출력은 분리합니다. SQLite DB와 기존 원본/출력은 함께 백업하고, v10 전환은 서버를 정지한 상태에서 비공개 DB 백업·무결성을 확인한 뒤 진행합니다. 이번 추가 마이그레이션은 기존 테이블을 삭제·재작성하거나 과거 AI 기록을 생성하지 않습니다.
