# 영구 변경 이벤트·순서별 재생

업무·첨부·분석 설정·집계 전환·검토 결정의 변경 알림을 SQLite에 영구 저장합니다. 서버가 재시작되거나 WebSocket 전송이 끊겨도 마지막 수신 커서부터 순서대로 이어받습니다. 이벤트는 화면을 갱신하는 읽기 알림이며 업무 실행 명령이 아닙니다.

## 기록과 마이그레이션

스키마 v9는 기존 테이블을 보존하고 `activity_streams`, `activity_events` 및 기록 트리거를 추가합니다. 계정별로 무작위 128비트 `stream_id`와 0부터 시작하는 순서 번호를 갖습니다. 이벤트의 기본키는 `(account_id, sequence)`이며 다른 계정의 변경 횟수가 번호에 드러나지 않습니다.

업무 변경과 이벤트 INSERT/순서 증가가 같은 DB 트랜잭션에서 수행됩니다. 별도 큐/워커 연결에서 확정한 전환도 기록합니다. 이벤트 기록에 실패하면 업무 변경도 롤백합니다. 기존 중복 방지 요청의 재전송·거부된 충돌·취소 재전송은 새 이벤트를 만들지 않습니다. 설정 저장은 성공한 새 버전마다 기록합니다.

| 종류 | 기록 시점 | 상태/버전 |
| --- | --- | --- |
| job.created | 계정 소유 업무 최초 생성 | received |
| job.imported | 유효한 익명 이력을 계정으로 가져옴 | received |
| attachment.added | 새 원본 첨부 확정 | 없음 |
| selection.saved | 열·설문 설정 저장 | 저장 revision |
| run.changed | 기존 실행 이벤트 기록 | queued/running/completed/failed/cancelled, 실행 revision |
| review.decided | 승인/반려 최초 확정 | approved/rejected |

각 이벤트에는 순서·종류·업무/파일/실행 ID·상태/버전·기록 시각만 담습니다. 제목·요청 내용·파일 이름/본문·요약 JSON·검토 의견·비밀번호/세션/복구 코드를 복사하지 않습니다. 이벤트 UPDATE/DELETE를 거부하며 현재는 자동 정리/보존 기한을 적용하지 않습니다. DB 백업에 이력과 커서가 함께 포함되며 원본/보관 결과는 기존처럼 별도 백업이 필요합니다.

v8까지의 과거 변경은 소급 생성하지 않습니다. 기존 계정은 순서 0의 기준점에서 시작하고 첫 접속은 현재 상태를 조회합니다. v9 이후 확정한 변경만 영구 재생 대상입니다. 마이그레이션 실패는 추가 스키마 전체를 롤백하고 연결을 닫습니다. 사용자 DB 적용 전 비공개 DB 백업과 무결성/외래 키 검사를 수행합니다.

## 전송 계약

`/api/jobs/updates?account=<계정 UUID>&cursor=<stream_id>:<sequence>`

cursor는 선택 항목이며 세션이나 권한 증명이 아닙니다. 기존 동일 Origin·HttpOnly 쿠키·계정 검사와 계정당 8개/전체 256개 연결 제한을 유지합니다. 알 수 없는/중복 쿼리와 잘못된 커서 형식은 400입니다. 순서는 선행 0·부호·소수·지수 없는 0 이상의 안전한 정수(최대 9,007,199,254,740,991)입니다.

1. `ready`: `{type, cursor, head, reset}`. 기준 커서와 현재 계정의 최신 순서를 알립니다. 유효한 이전 커서는 reset=false로 시작합니다. 첫 접속, 다른 계정/DB의 stream, 최신 번호보다 큰 커서는 reset=true로 현재 기준점을 반환하고 화면 전체를 다시 조회합니다. 다른 계정의 이벤트는 반환하지 않습니다.
2. `events`: `{type, streamId, from, to, head, events}`. `(from,to]` 구간의 연속된 이벤트를 최대 100개씩 오름차순으로 전달합니다. 첫 묶음은 접속 직후, 나머지는 서버 확인 주기(기본 1초)마다 전달합니다. to<head이면 ‘누락 변경 복구 중’, 따라잡으면 ‘자동 갱신 연결됨’으로 표시합니다.
3. `heartbeat`: `{type, cursor}`. 새 이벤트가 없으면 15초마다 현재 커서를 확인하고 목록 조회 실패를 다시 확인합니다. ping/pong은 변경이 계속 있어도 독립적으로 확인합니다.

매 묶음 전 세션과 송신 적체를 다시 검사합니다. 만료/회수된 연결은 종료하며 64KiB 초과 송신 적체도 종료 후 재연결로 복구합니다. 저장 이력의 순서가 빠졌거나 서버 기준점이 이전으로 바뀌면 reset=true를 알리고 현재 상태를 조회합니다. 정상 경로는 이력을 삭제하지 않으며, 이 재설정은 비정상 복원/이력 손실의 안전한 대체 경로입니다.

## 브라우저 수신과 화면 상태

브라우저는 메시지 전체의 종류·순서·ID·기본 메타데이터를 검사한 후 커서를 전진시킵니다. 겹치거나 중복된 이벤트는 이미 받은 부분을 다시 적용하지 않으며, 순서 누락·역순·다른 stream·잘못된 데이터는 연결을 닫고 마지막 유효 커서부터 다시 받습니다. 커서는 계정별 탭의 sessionStorage와 메모리에 보관합니다. 저장소가 차단되면 같은 화면의 메모리 커서로 복구합니다. 새 탭/커서 유실은 최신 기준점과 전체 조회로 시작합니다.

**커서는 이벤트 수신 확인 위치입니다. HTTP 조회 완료나 업무 실행 완료를 뜻하지 않습니다.** 접속/재접속/재설정 직후에는 항상 최신 GET을 수행하고, 변경 묶음마다 현재 조건으로 조회합니다. HTTP 실패는 마지막 데이터·입력과 오류를 유지하며 다음 확인 주기 또는 명시적 새로고침으로 재조회합니다. 최종 화면은 서버의 최신 상태를 표시하므로 짧은 과거 상태를 애니메이션으로 모두 재현하지는 않습니다. 감사용 과거 순서는 DB 이벤트에 보존합니다.

검색 조건·더 보기 깊이·선택한 결과·미제출 입력 유지 규칙은 [자동 갱신 안내](JOB_UPDATES.md)를 따릅니다. 재생은 POST·집계 접수·취소·검토 결정을 다시 실행하지 않습니다. 정확히 한 번의 외부 부작용이나 DB 유실 후 복원을 보장하는 기능이 아닙니다. 과거 백업 복원으로 사라진 이벤트는 재생할 수 없습니다.

전체 업무 상태 모델/캐릭터 연결·실제 AI·운영 TLS 프록시·다중 프로세스 성능·보존/삭제 정책은 후속 작업입니다. 이번 프로토콜로 바뀐 서버에 연결한 이전 UI는 새로고침해 같은 버전의 UI를 받아야 합니다.
