# 백그라운드 집계 작업

파일 미리보기에서 열·설문 설정을 저장한 뒤 **백그라운드 집계 접수**를 누릅니다. 저장한 원본 해시와 설정 버전으로 정량 집계를 접수하고 대기·실행·완료·실패·취소 이력을 DB에 보관합니다. 화면을 닫거나 로그아웃해도 서버는 작업을 계속 처리합니다. 같은 계정으로 로그인하고 같은 파일을 열어 이력과 결과를 확인합니다.

업무 접수 기록의 `received`/`not_connected`와 파일 집계 실행 이력은 별개입니다. 업무를 저장하는 것만으로 큐를 시작하지 않습니다. 오피스 캐릭터는 여전히 시뮬레이션이며 실제 AI·Python·Codex 호출은 없습니다.

## 상태와 복구

| 상태 | 의미 |
| --- | --- |
| queued / 대기 | 원본/설정 버전을 접수하고 실행 순서를 기다림 |
| running / 실행 중 | 워커를 시작하고 원본을 검증·계산하는 중 |
| completed / 완료 | 설정 버전을 재검증한 뒤 요약·파일 3종의 보관을 확정함 |
| failed / 실패 | 원본·설정 변경, 파싱/한도/실행 오류, 시간 초과 또는 서버 중단 |
| cancelled / 취소됨 | 사용자가 대기·실행 작업을 취소함. 이후 결과는 게시하지 않음 |

대기 작업은 접수 순서대로 하나씩 실행합니다. 상태 전환과 이벤트를 같은 DB 트랜잭션으로 기록합니다. 취소와 완료가 겹치면 먼저 저장된 최종 상태를 보존하며, 완료·실패·취소된 작업의 취소 요청은 상태를 바꾸지 않습니다. 실행 중 취소는 상태를 먼저 기록하고 다음 큐 주기에서 워커를 종료합니다.

정상 종료 시 실행 중인 작업은 실패로 기록하고 스레드를 종료하며 대기 작업은 보존합니다. 강제 종료 후에는 DB 큐 소유권(lease)의 10초 유효기간이 지난 뒤 새 서버가 이전 실행 작업을 실패로 복구합니다. 대기 작업은 재개하지만 실패 작업은 자동 재시도하지 않습니다. 새 작업으로 접수해야 합니다. 화면은 진행 중인 목록을 약 1초마다 갱신하고 연결 실패 시 새로고침 버튼으로 다시 조회합니다. 가상의 진행 퍼센트는 표시하지 않습니다.

## 버전·결과·원본

접수 시 저장한 시트·제목 행·선택 열·설문 문항·버전·원본 SHA-256을 스냅샷으로 기록합니다. 실행 직전 현재 저장 버전을 확인하고 워커가 원본 크기·SHA-256을 확인합니다. 완료 저장 직전에도 버전을 재검증합니다. 대기/실행 도중 설정이 바뀌면 해당 실행을 실패 처리하고 결과를 보관하지 않습니다. 원본·설정·업무 접수 상태는 실행으로 변경하지 않습니다.

완료된 JSON 결과는 생성 당시 기록입니다. 완료 후 설정을 바꾸거나 새 작업을 접수해도 예전 결과를 덮어쓰지 않습니다. 결과에는 원본 해시·설정 버전·계산 시각, 전체/열별 건수·숫자 통계·설문 통계·상위 30개 빈도·나머지 합계를 보관합니다. 긴 빈도 값은 화면과 동일하게 200자 표시입니다. 문항 통계/숫자 처리 기준은 기존 집계와 같습니다.

완료된 실행에는 CSV·HTML·XLSX도 보관하며 저장 결과에서 당시 파일 그대로 내려받습니다. **기존 선택 열 기초 집계의 다운로드는 현재 저장 설정으로 다시 계산하는 별도 기능**입니다. 이전 완료 작업의 파일 없는 경우·저장 경로·무결성·백업·정리는 [실행 결과 파일 안내](RUN_ARTIFACTS.md)를 참고하세요.

## 실행 한도·구조

- 서버가 큐를 약 250ms마다 확인하고 Node.js worker_threads에서 한 번에 한 작업을 처리합니다. 큐 소유권과 최종 상태 검사가 이전 워커의 늦은 결과 저장을 막습니다. 동일 DB를 여러 서버에서 공개 운영하는 구성은 별도 검증이 필요합니다.
- 전체 대기+실행 작업 20개, 계정당 5개를 넘으면 429입니다. 같은 요청의 재전송은 한도에 도달해도 기존 접수 결과를 반환합니다.
- 워커 기본 타이머는 15초, V8 old generation 128MiB·young generation 16MiB·stack 4MiB입니다. 입력 5MiB/파일 및 행·열·셀 파싱 제한은 유지합니다. 스레드 타이머/힙 한도이며 OS 프로세스 격리·총 RSS 상한은 아닙니다. API 이벤트 루프가 지연되면 타이머/취소 동작도 지연될 수 있습니다.
- 결과 JSON은 작업당 5MiB 이하입니다. DB에는 이제 원본에서 계산한 값도 들어갑니다. 계정 소유자만 결과를 조회하며 DB·원본·비공개 백업은 외부 공유나 Git 커밋 대상이 아닙니다.
- 이력/파일 자동 삭제·전체 디스크 사용량 제한·분산 큐·운영 관측·WebSocket은 후속 과제입니다. 기존 동기 집계/내보내기 경로는 그대로 유지되므로 모든 파일 처리가 워커로 이동한 것은 아닙니다.

## API

경로 접두사는 `/api/jobs/:id/attachments/:fileId/runs`입니다. 유효한 세션과 해당 첨부의 소유권을 요구하며 모든 응답은 no-store·nosniff입니다.

| 메서드·경로 | 동작 |
| --- | --- |
| POST 접두사 | JSON `{ "revision": 1 }`, `Idempotency-Key`로 접수. 신규 202, 재전송 200 |
| GET 접두사 | `limit` 1~20, `offset` 0 이상. `{ runs, page }` 이력 페이지 |
| GET `/:runId` | `{ run, events }` 상태·시간·오류와 전환 이력 |
| GET `/:runId/result` | 완료 시 `{ summary, artifacts, reviewTargetHash }`, 완료 결과 없으면 409 |
| GET `/:runId/artifacts/:format` | 완료 당시 csv/html/xlsx 파일, 무결성 실패 409·없는 파일 404 |
| POST `/:runId/cancel` | JSON `{}`로 대기/실행 취소. 최종 상태면 그대로 반환 |

쓰기에는 동일 Origin·JSON·`X-Office-Request: 1`이 필요하고 UI는 `X-Office-Account`도 보냅니다. 세션 실패 401, 다른 계정·다른 첨부·없는 ID는 404, 본문/식별자 오류는 400입니다. 본문에서 임의 파일 경로·열·설문 설정·상태를 받지 않습니다.

요청 키는 계정 범위이며 같은 업무/첨부/선택 버전이면 기존 작업을 반환합니다. 같은 키의 다른 요청은 409입니다. 접수 응답이 유실되면 같은 키로 재시도하세요. 이미 접수한 요청의 재전송은 이후 설정이 바뀌어도 원래 작업을 복원하며, 새로운 버전의 실행은 새로운 키가 필요합니다. UI는 네트워크 실패 시 키를 유지하고 정상 응답 후 새 접수를 구분합니다.

v6는 기존 테이블을 유지하며 `summary_runs`, `summary_run_events`, `summary_queue_lease`를 추가합니다. Node 24의 직접 TypeScript 실행과 빌드 후 JavaScript 워커 경로를 모두 지원합니다. API 서버 정상 종료 시 큐를 먼저 종료한 뒤 DB를 닫습니다.

v7은 기존 실행 요약을 유지하며 파일 메타데이터 테이블을 추가합니다. 과거 완료 실행의 파일은 소급 생성하지 않습니다. DB·입력 원본·출력 파일을 함께 백업하세요.

v8의 실행 결과 승인·반려·해시 연결·검토 이력은 [결과 검토 안내](RESULT_REVIEW.md)를 따릅니다.
