# Codex 통신·단일 텍스트 실행 어댑터

2026-10-22 기준 CLI **0.163.0**의 비공개 stdio 통신과 단일 텍스트 업무의 인증·thread/turn·중단 계약을 구현했습니다. 실제 CLI에서는 초기화와 미인증 상태만 확인했습니다. 실행 흐름은 합성 stdio 서버로 검증했으며 실제 모델 호출은 수행하지 않았습니다. 이후 [영구 AI 큐·계정별 API](AI_QUEUE.md)에 합성 실행 계약을 연결했습니다. 기본 서버의 실제 모델 디스패치는 미연결이며 오피스에는 별도 [AI 메타데이터 기록](AI_STATUS.md)만 표시합니다.

## AI 호출 없는 검사

현재 Linux 실행 서버·Node.js 24 이상에서 검증했습니다. 신뢰하는 Codex 0.163.0 실행 파일을 별도로 준비합니다. CLI를 저장소에 포함하거나 자동 설치하지 않습니다.

```sh
OFFICE_CODEX_BIN=/absolute/path/to/codex npm run check:codex
```

`codex-cli 0.163.0` 버전 문자열, `app-server --listen stdio://`, `initialize` → `initialized`, `account/read`의 account=null을 확인하고 종료합니다. 로그인·thread/turn·모델·과금 검사는 하지 않습니다. 기본 개발 서버와 빌드는 이 명령을 실행하지 않습니다. CLI 설치 없이 기존 앱과 정량 집계를 사용할 수 있습니다.

## 서버 전용 실행 설정

`backend/src/codex/execution.ts`의 `CodexExecution`은 실행 파일 절대 경로, 별도로 제공한 제품용 `serviceApiKey`, 명시적인 모델·정수 `maxRunMs`, 아래 운영자 확인 설정을 모두 요구합니다.

- `allowPaidCalls: true`: 서비스 계정·비용 조건을 확인했다는 호출자의 설정
- `allowDataTransfer: true`: 입력을 제공자에게 전송하는 조건을 확인했다는 호출자의 설정
- `executionIsolationReviewed: true`: 실제 실행 호스트의 격리·접근 범위를 검토했다는 호출자의 설정

이 값은 HTTP 요청 본문에서 받아서는 안 됩니다. 기본 서버는 이 설정을 만들거나 키를 읽지 않습니다. 별도 운영자 명령만 [제품용 연결 설정](AI_SERVICE_CHECK.md)의 비공개 파일에서 명시적으로 읽습니다. 부모 환경의 API 키나 개발 세션 인증을 자동으로 사용하지 않습니다. 별도 서비스 키는 서버 비밀 저장소에서 제공해야 하며 브라우저·DB·로그에 넣지 않습니다. API 키 로그인과 읽기 확인 코드는 합성 응답으로만 검증했습니다. 유효한 서비스 인증·모델 접근·이용 조건·보존 정책·과금은 아직 검증하지 않았습니다.

`maxRunMs`는 50~120,000ms이며 초기화·인증·모델 처리를 포함합니다. 요청 대기는 기본 10초, 중단 유예는 기본 1.5초(50~5,000ms)입니다. 한 인스턴스는 한 turn만 전송하며 자동 재접속·재전송을 하지 않습니다. 이는 금액 상한이 아니며 App Server 내부 재시도까지 없애는 설정도 아닙니다. 실제 배포 전 제공자 측 비용 제한이 필요합니다.

## 실행·이벤트·결과

1. `run(jobId, text)`는 1~128자의 영숫자/밑줄/하이픈 ID와 비어 있지 않은 UTF-8 텍스트 16KiB 이하를 검사합니다. jobId는 상관관계 키이며 소유권을 증명하지 않습니다. 실제 업무 큐 연결 시 기존 계정 권한을 별도로 확인해야 합니다.
2. 격리된 App Server 초기화 후 `account/login/start`의 API 키 방식과 `account/read`의 API 키 계정 유형을 확인합니다. 그 뒤 요청 모델·임시 cwd·ephemeral·untrusted 승인·readOnly/네트워크 false 정책과 일치하는 thread 응답을 요구합니다.
3. `turn/start`를 한 번 전송하고 응답의 turn ID를 업무/thread ID와 묶습니다. 응답보다 먼저 오는 관련 알림은 최대 64개 버퍼링하며 다른 thread의 출력은 반영하지 않습니다. 같은 thread의 다른 turn은 오류입니다.
4. 정규화한 이벤트는 starting/running/cancelling/종료 상태·업무 ID·순서만 포함합니다. 프롬프트·키·원격 오류·추론·생성 본문을 이벤트에 넣지 않습니다. 현재는 인스턴스 내 읽기용이며 SQLite 영구 이벤트와 연결하지 않았습니다.
5. 완료된 agentMessage의 명시적인 `final_answer`만 수집합니다. null/부분 답변/해설만 있는 완료, 빈 결과, 16KiB 초과, 같은 item ID의 내용 충돌은 성공으로 처리하지 않습니다. 현재 지원 모델 범위가 좁아 phase를 생략하는 제공자는 별도 호환 검증이 필요합니다.
6. `turn/completed`의 상태·오류·수집한 출력도 함께 검사합니다. 성공 텍스트는 `needsReview: true`이며 자동 승인·저장·파일 생성·외부 발송을 하지 않습니다. 텍스트의 사실성은 검증하지 않았으며 [AI 초안 화면](AI_UI.md)에서도 원문을 HTML로 실행하지 않습니다.

요청·응답 ID는 초기화부터 순차 발급합니다. 서로 다른 요청을 대응시키며 중복/알 수 없는 응답·잘못된 필수 필드는 연결을 종료합니다. 같은 jobId와 동일 입력의 재요청은 같은 Promise/결과를 반환합니다. 다른 ID나 다른 입력은 conflict이며, 이 보장은 인스턴스 수명 내에만 적용됩니다. 새 프로세스·새 인스턴스·서버 재시작을 넘는 중복 실행 방지는 어댑터 단독으로 제공하지 않으며 영구 AI 큐에서 관리합니다.

## 중단과 실패

- `cancel(jobId)`는 같은 업무에 중복 호출해도 turn/interrupt를 한 번만 보냅니다. turn 시작 응답 유실 중에는 ID를 기다리며 유예 시간 안에 확인하지 못하면 닫습니다. 시작 전 중단은 turn을 보내지 않습니다.
- interrupt RPC 응답은 접수 확인입니다. 원격 `turn/completed: interrupted`가 와야 `remoteStatus: interrupted`로 기록합니다. 응답만 오거나 유예 시간이 지나면 `remoteStatus: unknown`, `interrupt_unconfirmed`입니다. 이미 완료된 뒤 취소를 요청한 경우 원격 상태 completed를 유지하고 출력은 버립니다.
- 전체 시간 초과는 timed_out, 통신·정책·잘못된 결과는 failed입니다. App Server 내부의 재시도 가능 error 알림도 전체 시간 제한 안에서만 기다립니다. 원격 실패 본문은 결과/오류에 복사하지 않습니다. 시작 응답을 잃어도 turn/start를 재전송하지 않습니다.
- 모든 종료 결과는 자식 프로세스와 임시 폴더 정리를 기다린 뒤 반환합니다. 호출자는 `try/finally`에서 `await execution.close()`를 호출해야 합니다. 강제 종료는 제공자 측 요청 취소·과금 중단을 증명하지 않습니다.

## 격리와 도구 범위

연결마다 권한 0700의 임시 HOME/CODEX_HOME/cwd를 만들고 부모 환경을 상속하지 않습니다. 자식 환경은 HOME, CODEX_HOME, PATH(`/usr/bin:/bin`), TMPDIR뿐입니다. 키는 환경이 아닌 비공개 stdio 로그인 요청으로 전달하고, CLI가 임시 인증 파일을 만들 수 있는 CODEX_HOME은 종료 시 제거합니다. stdout은 프로토콜 파싱 전용이며 stderr는 저장 없이 비웁니다.

모든 서버 요청은 `-32601`로 거부하며 실행 어댑터는 approval_required로 중단합니다. 현재 지원 item은 텍스트·추론·계획·사용자 메시지뿐이며 명령/파일/검색/도구 item을 받으면 실패합니다. 다만 **읽기 전용 Codex 정책과 item 감지는 호스트의 완전한 격리나 모든 도구의 사전 차단을 보장하지 않습니다.** 도구가 알림 전에 실행될 수도 있으므로 실제 키·개인정보를 제공하기 전에 별도 컨테이너·네트워크·읽기 권한을 검토해야 합니다. 이번 작업에서는 실제 도구 실행을 하지 않았습니다.

버전 검사는 신뢰할 수 없는 실행 파일의 진위를 보증하지 않습니다. 운영자가 바이너리와 호스트를 관리해야 합니다. 셸로 실행하지 않으며 절대 경로만 받습니다. 버전 확인 프로세스는 제한 시간 또는 연결 취소 때 SIGKILL, App Server는 SIGTERM 뒤 500ms에 SIGKILL합니다. 연결당 송수신 각각 1MiB·줄당 64KiB, 동시 RPC 최대 4개·요청 ID 31개 제한을 유지합니다. 전체 생성 스키마가 아닌 좁은 프로토콜 부분집합을 검사합니다.

## 출처·검증·남은 작업

[0.163.0 공식 App Server 문서](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/app-server/README.md)와 실제 `generate-ts`의 Initialize/Account/ThreadStart/TurnStart/Turn/ThreadItem/TurnInterrupt 타입을 확인했습니다. CLI는 실험적 인터페이스이며 업데이트 시 계약 검사가 필요합니다.

합성 프로세스는 가짜 키·합성 텍스트만 사용하며 관측 로그에서도 키와 입력을 가립니다. 초기화·인증·정상 완료·조기/중복/다른 thread 이벤트·잘못된 정책·빈/부분/과도한 답변·서버 승인 거부·RPC 응답 유실·중단 확인 누락·시간 제한을 검사합니다. 실제 CLI 초기화/미인증 검사와 합성 실행 검사의 증거를 구분합니다.

영구 AI 큐·소유권·재시작 중복 방지는 별도 모듈에 구현했습니다. 운영자 단일 호출 명령과 AI 검토 기록 저장은 구현했습니다. 남은 작업은 실제 운영 조건·가상 데이터 실제 호출 검증, 서버 디스패치 활성화, 파일 산출물 검증과 도구 승인 정책입니다. 기존 정량 집계·업무 결과 승인과 이번 실행 상태는 별개입니다.
